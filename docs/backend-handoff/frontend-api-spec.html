Overview

1. 전체 공통 규칙

백엔드/ERD 구조는 프론트 때문에 바꾸지 않음

  • Customer / Visit / VisitRecord 분리
  • Interest / Purchase / Stamp / AI Brief 별도 테이블
  • CA storeId는 JWT 기반
  • Visit 중심 업무 흐름
  • Gemini Brief 5개 필드 구조

프론트가 반드시 맞춰야 하는 핵심

  • 보호 API는 실제 JWT 기준으로 호출
  • 응답은 ApiResponse / PageResponse 처리
  • CA 임의 매장 선택 제거
  • QR 조회는 customerNo가 아니라 qrToken
  • Visit 생성 후 visitId 상태 관리
  • VisitRecord DELETE 없음
  • AI Brief latest는 visitId query 필수

중요

AI Brief

12. AI Brief API

현재 상태
MySQL/Gemini 실검증은 아직 미실행 상태입니다. 현재 로컬 안전 모드 기준으로 AI Brief 생성의 실제 외부 Gemini 호출은 비활성 상태입니다. 다만 API 계약 자체는 이후 외부 연동 시점에도 유지되도록 설계되어 있습니다.
POST/api/v1/customers/{customerId}/ai-briefs
{
  "visitId": 101
}
GET/api/v1/customers/{customerId}/ai-briefs/latest?visitId=101

권한: CA · latest는 GENERATED/FAILED 포함 최신 생성 시도 기준

GET/api/v1/customers/{customerId}/ai-briefs?page=0&size=20

권한: CA · 조회 API는 Gemini 재호출 없음
